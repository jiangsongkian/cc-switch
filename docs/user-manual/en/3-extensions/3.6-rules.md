# 3.6 Rules Management

## What Rules Do

Rules are reusable instructions that can be shared across apps. A Prompt allows only one active entry per app and replaces the target file; any number of rules can be active at once, and the same rule can be toggled independently in each app.

- The rule content is stored only once in CC Switch. The database is the single source of truth; each app's rules directory is a projection that is rewritten when a rule is enabled, disabled, renamed, or deleted.
- The current version supports user-level (global) rules for **Claude Code**, **Codex**, **Gemini CLI**, and **OpenCode**. Codex has no rules column on Windows. Other apps do not appear on the Rules page and receive no files.
- The matrix only shows apps enabled under **Apps shown in the sidebar** in Settings; rules for hidden apps are still synced in the background.

## Open the Rules Page

Click **Rules** in the sidebar. The page header has only **Add rule** on the right. The page has two tabs:

- **Installed**: rules managed by CC Switch, shown as a rule × app matrix.
- **Discover**: rule files that already exist in a supported app's rules directory but are not managed yet.

Both tabs have a search box in the top-right corner that filters the current tab only.

## Create and Edit Rules

Click **Add rule** in the header to create a rule, or click a rule name in Installed, or use ⋯ → **Edit**. Both open the same dialog.

- **Name** is required and is also the file name: `<name>.md`. Pressing Enter in the name field saves.
- Names are compared case-insensitively. They cannot contain `/ \ < > : " | ? *` or control characters, cannot start or end with `.`, cannot use Windows reserved names such as `CON` or `COM1`, and are limited to 80 characters.
- **Content** is Markdown, up to 256 KiB.
- **Save** is available only when something changed and there are no errors; the dialog cannot be closed while saving; closing without saving discards changes.
- Saving syncs to every app immediately. A new rule is not enabled anywhere until you tick cells in the matrix.
- Renaming is renaming the file: the old file is removed from each app's directory and the new name is written.

## The Installed Matrix

Each row is a rule; each column is an app. The header and rule names stay fixed while scrolling.

- **Row**: checkbox, rule name (click to edit), and a content preview. A rule enabled nowhere is marked **Not enabled**; a failed write shows ⚠ next to the name with the error on hover.
- **Cell**: click to write or remove the rule file in that app. A cell can be enabled, disabled, or failed; click a failed cell to retry.
- **Column header**: shows how many rules are enabled in that app. Open it to enable all, disable all, or toggle a filter to that app. Bulk actions apply only to the current list (all / filtered / searched rows) and offer an undo toast.
- **Selection**: tick row checkboxes or the header checkbox. The toolbar then shows **N selected**, with **Enable in** / **Disable in** to sync the selection to an app, and **Clear selection**.
- **Filter**: the toolbar offers All / Enabled / Not enabled, which stacks with an app filter from a column header.
- **Search**: matches rule names and content; the number of matches is shown in the search box.
- **Sync to apps**: shown on the right of the toolbar when nothing is selected; reprojects every rule according to its switches, repairing inconsistencies caused by external edits. CC Switch also syncs on startup, on save, on cell toggles, on delete, and on import.
- **Row menu ⋯**: edit, delete. Deleting asks for confirmation and removes the rule files from every app.

With no rules at all, the page offers **New rule** and **Go to Discover**. When a search or filter matches nothing, it offers a clear-search or clear-filter button.

## Discover and Import

The Discover tab lists only rule files that are **not managed yet**; added files do not appear here.

It scans the rules directories of supported apps and considers `.md` files directly inside the directory; hidden files and subdirectories are skipped, as are files whose names cannot be used as rule names (too long, containing `/`, Windows reserved names, leading/trailing spaces, and so on). A same-named file in several apps is shown once, and its content comes from the first copy read in `Claude Code → Codex → Gemini CLI → OpenCode` order.

Each row shows the file name, full path, a content preview (skipping frontmatter and headings), the app icons where it was found, and an **Add** button. Search matches the name, path, preview, and app names.

Clicking **Add**:

- imports the content into CC Switch and enables it in every app where it was found; edit it in Installed afterwards;
- does not overwrite an existing rule with the same name (such files are not listed anyway);
- imports each file only once;
- if registering an existing file fails for one app, that app stays disabled and a warning is shown; other apps are unaffected;
- scanning only reads. Importing is what writes the database, the `.cc-switch-rules.json` manifest, and the projected files. Same-named files in other apps are rewritten from the imported content, so frontmatter may be stripped.

**Rescan** in the top-right refreshes the list; it also refreshes when the window regains focus. The header shows **N to add**. When nothing is left to add, the list says so; when a rules directory is empty, it suggests creating a rule or dropping files in and rescanning.

## How a Rule Is Installed: Three Fixed Steps

Whether an app reads rules natively or needs help, CC Switch always runs the same three steps in the same order:

1. **Confirm the install location**: resolve the `rules` directory under the app's config directory and the extension (`.md`).
2. **Write the rule file**: render the body into a format the app understands and write `<name>.md`.
3. **Make the app read it**: Claude Code reads the directory natively, so this step is a no-op; Codex and Gemini CLI add or remove a SessionStart hook; OpenCode adds or removes the rules glob in the global config.

If step 3 fails, the file from step 2 is kept, the error names the step, and the next sync retries only the failed part. When the last rule for an app is disabled, step 3 undoes the hook or glob it installed.

## Per-App Adaptation

| App         | How rules are read  | Rules directory                 | What step 3 changes                                                                                                | Notes                                                                         |
| ----------- | ------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| Claude Code | Read natively       | `~/.claude/rules/*.md`          | Nothing                                                                                                            | Keeps YAML frontmatter; `paths:` works                                        |
| Codex       | SessionStart hook   | `~/.codex/rules/*.md`           | Adds a SessionStart entry to `~/.codex/hooks.json`; turns on `[features] codex_hooks` in `config.toml` when needed | Unavailable on Windows, column hidden; requires trusting the hook in `/hooks` |
| Gemini CLI  | SessionStart hook   | `~/.gemini/rules/*.md`          | Adds a `cc-switch-rules` SessionStart hook to `settings.json`                                                      | The hook returns strict JSON `additionalContext`                              |
| OpenCode    | `instructions` glob | `~/.config/opencode/rules/*.md` | Adds or removes one absolute-path glob in `instructions` of `opencode.jsonc` (when present) or `opencode.json`     | Preserves comments, formatting, and other entries                             |

General constraints:

- Most apps read rules at **session start or on the first request**; open a new session after a change, and restart OpenCode.
- Only Claude Code keeps YAML frontmatter as written; every other app gets it stripped.
- Rules directories follow a config directory overridden in Settings.
- Hook apps inject every `.md` in the rules directory, including files not managed by CC Switch, joined in file-name order. Injected text counts against the context window, so keep rules short.
- Disabling rules does not turn `codex_hooks` back off (you may have enabled it yourself).

## File Ownership, Conflicts, and Cleanup

CC Switch maintains a `.cc-switch-rules.json` manifest in each rules directory, recording the rule file names it wrote:

- Disabling or deleting a rule removes only the files listed in the manifest; `.md` files you place there yourself are never deleted, and hook apps keep reading them while rules are enabled.
- Do not edit CC Switch-generated files directly: the next save, toggle, or startup overwrites them. Edit rules on the Rules page instead.
- If the target already contains a same-named file that is not in the manifest, the sync reports a conflict instead of overwriting it (files with identical content are accepted). Import it from Discover first, or rename it manually and enable the rule again.
- If you switch an app's config directory in Settings, CC Switch regenerates rule files in the new directory. Files in the old directory are not cleaned up automatically.
- If the manifest is malformed or contains unsafe file names, those entries are ignored and nothing is written outside the rules directory.

## FAQ

**I saved a rule, but the app does not see it.**

- Claude Code: check that `~/.claude/rules/<name>.md` exists, then open a new session.
- Codex: check that you are not on Windows, `~/.codex/hooks.json` has the cc-switch SessionStart entry, `codex_hooks = true` is set in `config.toml`, and the hook is trusted in `/hooks`; then open a new session.
- Gemini CLI: check that `~/.gemini/settings.json` contains the `cc-switch-rules` SessionStart hook, then open a new session.
- OpenCode: check that the global config's `instructions` contains the rules directory glob, then restart OpenCode.

**Do rules conflict with prompts?**

No; they write to different places. For Claude Code, prompts are `CLAUDE.md` and rules are in `rules/`; for Codex and OpenCode, prompts are `AGENTS.md` and rules are referenced through a hook and `instructions` respectively; for Gemini CLI, prompts are `GEMINI.md` and rules are injected by the hook.

**Why is an app missing from the matrix?**

- Codex does not support rules on Windows.
- Other apps are not supported yet and never appear on the Rules page.
- The app may be hidden under **Apps shown in the sidebar** in Settings. Hiding only affects the UI; rules already enabled for that app keep syncing.
